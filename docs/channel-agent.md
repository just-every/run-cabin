# Channel browser agent

19 October 2026. The owner selected computer use in the host’s own channel accounts. The homepage stays unchanged. The module supports calendar actions and explicit source-table reads; no real channel account has been entered or proved.

## Use the core

1. Open **Channels → Channel agent** as the installation owner. Create a runner credential and save the shown JSON in a file readable only by you: `chmod 600 /absolute/path/private-runner.json`. It expires after 24 hours; replacing it revokes the previous credential.
2. For calendar automation, add `modelEndpoint`, `modelKey` and `model` to that private JSON. The endpoint must be an HTTPS vision-capable Responses (`/responses`) or Chat Completions (`/chat/completions`) service. The runner sends redacted operational screenshots and page text to that service; choose a provider you authorize to process this data. Missing model configuration stops with **Needs you**.
3. In the installed checkout, run `node scripts/channel-agent/index.mjs --config /absolute/path/private-runner.json`. Keep it running on the host’s computer. The existing Playwright dependency needs its current Chromium headless shell installed (`pnpm exec playwright install chromium`); system Chrome is never used.
4. Connect the home, channel, stable channel listing ID and host listing URL without query parameters. This first module maps **one listing per channel**, with one isolated session per installation/channel. The three mappings may represent the same physical home.
5. Open the localhost address printed by the runner. Click/type in this ephemeral profile viewer, complete sign-in yourself, open the host calendar, then choose **Finished**. Session state goes directly to Cabin encrypted with the installation’s existing session-secret sealing. Passwords/session state never enter the action log, model requests or evidence.

All confirmed booking commits—including iCal reads, direct checkout and host-entered stays—queue a close for the same home on every other mapped channel. The runner uses observed DOM references, at most 20 steps at human pace, and verifies each night after reloading before reporting success. Before/after screenshots and outcomes appear in the owner’s **Channel action log**; screenshots are encrypted at rest and served only through an authenticated owner door.

CAPTCHA, two-factor sign-in and bot checks stop automation and mark the profile **Needs you**. Choose **Resume sign-in**, finish the check yourself in the same profile viewer, then resume a stopped action. Security/sign-in images are ephemeral and never retained. Safe pre-write failures allow three attempts with backoff; ambiguous writes and expired leases become **uncertain**, require the host to check the channel, and are never replayed automatically. Disconnect forgets the saved session and cancels queued work; a running action must finish first.

**Undo: reopen nights** is offered only for a confirmed closure with a previously open baseline and an observed reopen control. Cabin refuses while any reservation/block still holds those nights. Reopening is itself logged and verified. Sign-in, security failures and uncertain writes have no undo.

## Read source pages into Cabin

19 October 2026, second module slice (SYNC-011, RES-002, MESSAGE-001 and FIN-002). Review the selected channel’s linked risk notice and grant session/action custody before connecting; pre-existing profiles must reconnect under this grant. Updated terms prompts now stop alongside CAPTCHA and two-factor challenges. Only the host may review or accept them.

On a connected profile choose **Read a channel page into Cabin**, select reservations, guest messages or settled payouts, paste the exact host page URL and confirm its listing. The runner opens that page without clicking or filling any control. This first reader supports visible HTML/ARIA tables with unambiguous headers and at most 100 rows. It does not navigate, paginate, download reports or infer absent records. Unsupported layouts, ambiguous columns or changing tables need the host. No current signed-in OTA layout has been established.

Only table headers go to the configured model. It selects column indices; source cell values are copied locally and never supplied to the model. Every row must carry the mapped channel listing ID; rows from another listing are refused. All required fields must be present: reservations need source ID, guest, exact ISO arrival/checkout dates and confirmed/cancelled status; messages need source reservation/message IDs, text, UTC sent time and explicit guest/host direction (host rows are not imported as guest messages); payout transactions need source transaction/batch/reservation IDs, settlement date, explicit USD gross/fee/net, transaction type and **paid/settled** status. Upcoming payments, virtual cards, property-collect balances and inferred fees are refused. Actual bank receipt remains separate evidence.

Reservations import through Cabin’s native inventory/lifecycle commands, retaining their actual channel reference and unknown prices/policies. Repeat reads deduplicate by channel/profile generation/home/source ID. Amendments update the same stay; explicit cancellations release it. An empty or inaccessible page never cancels bookings. Overlap, erasure, later local edits and conflicting source IDs require review. Guest messages enter the existing reservation-linked inbox and waiting-draft path. Equal names/emails alone do not merge identities; the operator reviews source references before joining guest histories. Browser reply sending is still unimplemented: a reply to a browser-read channel message visibly reports unavailable and directs the host to the channel, rather than selecting a different transport.

Payouts reuse the existing transaction CSV importer, matching the source reservation reference within the mapped home, retaining unmatched rows, rejecting changed transactions and avoiding duplicate native/manual imports. They do not post a second financial ledger. Source observations retain timestamps, scoped identities, record digests and the action reference, not another guest-message/contact corpus. Who requested the job, the runner’s owner, time, outcome and encrypted owner-only before/after screenshots are available in the channel log. Read-only source errors create an assigned exception without reporting a channel write or forcing sign-in; authentication/terms checks pause the profile.

Guest erasure withdraws the whole affected home’s source screenshots and read-page links because one table can contain several guests. Source anchors prevent restoration of erased contacts. Portable archives exclude browser sessions, runner secrets, evidence ciphertext and execution leases; restored profiles are disconnected and unfinished jobs are canceled. A restored archive cannot replay a channel action.

The five channel public-door tests use real Playwright against saved **synthetic** channel-edge pages, including all three reservation/message/payout reads, duplicate/restart handling, reviewed guest-thread joins, source amendments/cancellation, future payout refusal, unavailable pages, terms handoff, custody and erasure. They establish no live OTA DOM, guest receipt or bank acceptance. Channels, its connection/read forms and success/refusal log were used at 1440 and 390. SYNC-011, SYNC-002–004/006/007, MESSAGE-001 and FIN-002 retain their existing partial statuses; the next local slice is exact-approved browser replies, followed by owner-provided live-account acceptance.
