# Your direct-booking website

Open **Direct bookings → Your booking website** as the installation owner. Publish a host name, introduction, brand color, search description and privacy notice. Use the page editor to choose a unique address, title, plain-text content and optional search description. Content is escaped, never executable HTML. Your Cabin product homepage is separate.

Published homes appear at `/book`. Guests search dates, guest count and amenities against the same quote and inventory rules as checkout. Results show exact USD totals including fees and tax. A property page shows amenities, house rules, cancellation policy and optional local guide. Stripe payment, signed agreement, required Identity check and separate damage authorization stay attached to one direct reservation.

Property-team photos remain private. To publish a gallery, select its property photos in the website editor. Deleting a photo, withdrawing it from this list or unpublishing its home immediately refuses its public URL. Never select private completion photos, access credentials or sensitive instructions.

To use a custom domain, keep registration and DNS in your own account. Route its HTTPS traffic to this installation's Worker (Cloudflare Workers → Domains & Routes → Add custom domain), save the HTTPS origin in the editor, then **Verify custom domain**. Cabin requests a private per-installation challenge on that domain and enables guest requests only after it answers correctly. Browser form submissions must originate on that exact domain. Checkout return links stay on the guest's selected origin. The private operator app remains on its original origin. Changing or clearing the saved origin immediately revokes the old domain's booking access. When moving the installation, restore the backup, route the domain to the new Worker and verify again; no Cabin-owned domain or account is required.

Public pages expose escaped SEO descriptions, canonical URLs and `/book/sitemap.xml`; private reservation/task pages remain noindex. Optional analytics stores only anonymous daily page/path counts after the guest explicitly allows it. Decline stops subsequent counts. No third-party script, identity, query string or cross-site identifier is recorded. Website settings and page counts live in the owner's D1 and travel with ordinary installation backups. A restored custom domain must be verified again before use.

The public-door website test covers native multi-page form saves, exact photo bytes and publication withdrawal, current inventory search, owner-only settings, origin checks, domain verification/revocation and analytics consent. The archive journey retains public pages while withdrawing domain verification. The isolated hosted custom-domain journey used two homes and desktop/phone editor, search, gallery and checkout; its one reservation held USD 801.15 payment, the signed agreement, a consented manual identity decision and a separate USD 250 damage authorization before confirmation. Actual owner sign-in and guest receipt mail passed SPF, DKIM and DMARC.

## Embed booking on another website or WordPress

In **Direct bookings → Your booking website**, open the editor and save each allowed embedding origin, one per line, for example `https://host.example`. An origin includes the scheme, domain and any port; each subdomain needs its own entry. Only the installation owner can change this list. Removing an origin immediately withdraws its embedded catalog and its saved host-return links.

Open **Embed on your website or WordPress** and copy that origin’s iframe code. Replace `/booking` in its `embedReturn` parameter with your chosen HTTPS page on that authorized origin. Put it in your website’s HTML. In self-hosted WordPress, use a **Custom HTML** block with a user allowed to publish unfiltered HTML; save the page and inspect the published page. WordPress installations that remove iframes need their administrator to permit this block. Use an HTTPS Cabin installation or its verified custom domain; an HTTPS host page cannot embed an insecure production booking site.

The iframe has an accessible title, fills its container and scrolls independently. Date and guest inputs have labels and the ordinary booking forms work with a keyboard. Its catalog, live search, inventory, rules, exact prices, agreement and Stripe checkout are the hosted booking engine. Stripe opens in the full window on the guest’s own click. Success and cancellation return to the private Cabin stay page, which checks the real payment state; **Return to host website** then opens the chosen page without appending guest details, a reservation ID or a private stay token. That link remains available only while its origin is authorized. The external page never receives a claimed payment result from query parameters.

Only public catalog/content and price pages can be framed by the selected authorized origin. Private stay confirmations, guest records and the staff app retain their existing authorization and framing restrictions; no cross-origin staff API is enabled. Native booking POSTs retain Cabin’s existing origin checks. The browser sends only its origin as referrer, including when it leaves for Stripe.

`tests/website.test.mjs` covers shared pricing/inventory, exact-origin refusal, private-read refusal, one confirmed reservation and immediate revocation. `tests/website-browser.test.mjs` covers the owner form, external and Custom HTML iframe navigation, keyboard search, mobile layout, top-level Stripe navigation and one confirmation/return at 1440 and 390 pixels. Stripe is replaced only at the synthetic paid-network edge in this test. The local acceptance run also used an actual WordPress installation with a published Custom HTML block.
